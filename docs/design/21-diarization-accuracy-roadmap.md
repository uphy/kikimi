# 21. 話者分離 精度向上ロードマップ（候補整理）

対象読者: Kikimi 実装者（Claude Code 自身）。個別施策の実装前には本資料から詳細設計を起草すること。

参照元: `docs/design/13-speaker-diarization.md`（基本設計）,
`docs/design/20-voiceprint-misassignment-mitigation.md`（誤マッチ対策 M1〜M3）,
`docs/design/19-voiceprint-map.md`（Settings 話者タブ）。

本資料の位置づけ: 「話者分離の精度をさらに上げるには何ができるか」を、
**システム面**（モデル・照合・帰属アルゴリズム）と**ユーザーフィードバック面**（訂正・確認・事前情報の
活用）の両方向で棚卸しし、優先順位を付ける。個別施策の確定仕様ではなく、候補のカタログ + 推奨順序。

## 1. 現状ベースライン

実装済みの構成（design 13/20 の R1・R2・V1〜V3 完了時点）:

- **分離**: LS-EEND streaming（callhome variant / step 500ms / CPU）。DER 公称 26%。
  区間境界（Paused/Ended）で毎回 diarizer を再作成するため、同一人物の slot 分裂が構造的に起きる
- **帰属**: セグメント × turn の占有時間による多数決/混在表示。STT セグメント時刻は chunk 粒度
  （2240ms）の近似
- **照合**: WeSpeaker 256 次元 embedding。slot の発話が 5 秒（`min_enroll_speech_ms`）に達した時点で
  **一度だけ**抽出（直近 10 秒に打ち切り）し、閾値 0.45 + マージン 0.05 のオープンセット照合。
  全判定の距離ログ（M1）実装済み
- **学習**: **ユーザーの明示的フィードバック（slot リネーム・既知話者ピッカー・segment override）
  のみ**が声紋更新の対象。Ended 時に speaker あたり 1 回、α = 0.3 の EMA。auto 割り当てのまま
  Ended を迎えた slot は学習に使わない
- **救済**: 声紋リセット（embedding のみ破棄）、`.mixed`/同時発話サンプルの学習除外

計画済みで未実装のもの（既存設計に go/no-go 条件つきで載っている）:

- **R3**: トークンタイムスタンプによる混在セグメント分割（design 13 §12、スパイク 3 が前提）
- **複数声紋（multi-template enrollment）**: Phase 4 で声紋分裂の実測を見てから（design 13 §14）
- **オフライン再分離**: 破壊的な明示救済操作として将来追加可能（design 13 §14）
- **Sortformer backend**: 4 話者以下の会議向け改善候補（design 13 §2.1 備考）

## 2. 誤りの分類（どの誤りをどの施策が狙うか）

精度改善を語るとき「話者分離の誤り」は一枚岩ではない。パイプラインの層ごとに独立した誤りモードが
あり、施策ごとに効く層が違う。以下の分類を本資料全体のキーとして使う。

| ID | 誤りモード | 層 | ユーザーから見えるもの |
|---|---|---|---|
| E1 | 分離誤り（turn の併合・取りこぼし・過分割） | diarizer（LS-EEND） | 2 人の発言が 1 人にまとまる / 同一人物が短時間で slot を行き来する |
| E2 | 帰属誤り（turn とセグメントの対応付けミス） | セグメント帰属 | 相槌が直前の話者に付く / 混在表示が多すぎる |
| E3a | 照合の誤マッチ（別人を実名化） | 声紋照合 | 新しい参加者が既存の登録話者の名前で表示される |
| E3b | 照合のマッチ漏れ（本人なのに匿名のまま） | 声紋照合 | 毎回名前を付けた人が「Speaker N」に戻る |
| E4 | slot 分裂（世代跨ぎ・分離揺れによる同一人物の多重 slot） | coordinator | 一時停止のたびに「Speaker 5」「Speaker 6」が増える |
| E5 | 学習の遅さ・機会の少なさ | フィードバックループ | 訂正したのに同じセッション内では直らない / 訂正の手間が多い |

E3a は design 20 で集中対策済み。**現在の構造的な弱点は E3b（明示フィードバック限定の学習に
振ったことで、確認済みサンプルが増えにくい）と E4・E5** — つまり「誤らせない」方向は固まったので、
次は「正しく当てる回数を増やす」「訂正を安く・即座に効かせる」方向が主戦場になる。

## 3. システム面の改善候補

### 3.1 S1: 漸進的な再抽出・再照合（progressive re-matching）

- **狙う誤り**: E3b（マッチ漏れ）、E3a の一部（短サンプル起因の曖昧マッチ）
- **現状の制約**: 声紋抽出は slot あたり**一度だけ**、発話 5 秒到達時点（直近 10 秒に打ち切り）。
  会議冒頭の 5 秒は挨拶・かぶり・BGM が混ざりやすく、embedding の質が最も悪いタイミングで
  一発勝負している。閾値・マージンで棄却された slot は、その後どれだけクリーンな発話が
  溜まっても再挑戦しない
- **提案**: `extractedSlots` の one-shot 契約を「確定するまで再試行する」に緩和する。
  発話累計 5s → 15s → 30s の各到達点で再抽出・再照合し、(a) accepted になったら確定して打ち切り、
  (b) 30s 時点でも棄却なら匿名で確定。既に `.user` 割り当てがある slot・accepted 済み slot は
  再照合しない（現行の保護と同じ）
- **期待効果**: マージン/閾値棄却からの自動復帰。長いサンプルは embedding の分散が小さく、
  誤マッチを増やさずマッチ率だけ上げられる見込み
- **コスト**: 小。`RealtimeDiarizationCoordinator+Voiceprint.swift` の抽出トリガと
  `pendingSlotAudio` の保持を拡張するだけ。WeSpeaker 抽出は slot あたり最大 3 回に増えるが
  イベント駆動で負荷はほぼゼロのまま
- **リスク**: 再抽出のたびに判定が揺れると表示がチラつく。「accepted は一度きり・格下げしない」を
  不変条件にすれば防げる

### 3.2 S2: 抽出サンプルの品質ゲート（ライブ抽出への適用）

- **狙う誤り**: E3a / E3b（低品質サンプル起因の照合ブレ）
- **現状の制約**: override 学習（design 20 §5.3）は同時発話・`.mixed` を除外する保守的な
  切り出しを行うが、**録音中のライブ抽出はその slot の turn 範囲を無条件に採用**しており、
  overlap 区間（クロストーク）や極端に短い turn 断片も embedding に混入する
- **提案**: ライブ抽出の `pendingSlotAudio` 蓄積時に同じ品質規則を適用する:
  (a) 複数 slot の turn が同時に重なる区間を除外、(b) 一定長（例 300ms）未満の turn 断片を除外。
  design 20 §5.3 の切り出しロジックとヘルパを共有できる
- **期待効果**: 照合の入力品質が上がり、閾値・マージンの判定が安定する。S1 と併用すると
  「クリーンな発話だけで 15〜30 秒」の高品質サンプルになる
- **コスト**: 小〜中。turn 確定はストリームで届くため「その区間が overlap だったか」の判定に
  少し遅延バッファが要る
- **リスク**: 除外しすぎると `min_enroll_speech_ms` 到達が遅れ、実名化まで時間がかかる。
  S1 の多段トリガと組み合わせて緩和

### 3.3 S3: 世代跨ぎ slot の自動再連結（session 内声紋ブリッジ）

- **狙う誤り**: E4（slot 分裂）
- **現状の制約**: 一時停止・再開のたびに diarizer が再作成され、同一人物が新しい slot
  （Speaker N+1）として再出現する。声紋のグローバル DB にいる人は auto 照合で同じ実名に揃うが、
  **匿名のままの人・セッション内でリネームしただけの人は分裂したまま**で、ユーザーが毎区間
  リネームし直す羽目になる
- **提案**: 新世代の slot の embedding が抽出できた時点で、グローバル DB 照合の**前に**、
  同一セッション内の既存 slot の embedding（`speaker_assignments.json` に保存済み）と照合する。
  マッチしたら旧 slot の `display_name` / `global_speaker_id` を新 slot にコピーする
  （slot の統合はしない — design 13 §4.3 の「同一 global_speaker_id を複数 slot に割り当てて
  表示上 1 人に見せる」規約にそのまま乗る。セッションローカル名のみの場合も display_name の
  コピーで同じ効果が出る）
- **期待効果**: 「休憩を挟むと Speaker が増える」という最も分かりやすい体感劣化が消える。
  グローバル DB 未登録の会議（初対面ばかり）でも効く
- **コスト**: 中。照合先がセッション内に閉じるので誤マッチのリスク構造はグローバル照合より
  穏やか（候補が少ない + 同一会議・同一チャネルで embedding 条件が揃っている）。
  セッション内照合の閾値はグローバルの `speaker_match_threshold` より緩くできる可能性が高い
  （実測で決める）
- **リスク**: セッション内の 2 人の声が近い場合の誤連結。マージン判定を同様に適用して棄却する

### 3.4 S4: 複数声紋（multi-template enrollment）【計画済みの前倒し検討】

- **狙う誤り**: E3b（デバイス・媒体・声の調子によるチャネル分裂 → EMA のモード崩壊）
- design 13 §14 に設計要点が確定済み（speaker あたり最大 3 プリント・LRU 置き換え・
  最近傍照合・追加はユーザーフィードバック起点のみ）。go/no-go 材料の距離ログ（M1）も
  前倒し実装済みなので、**あとは実測データを集めて判断するだけの状態**
- **本資料での追加提案**: go 判断を早めるため、距離ログの集計を §5.2 の計測基盤に組み込み、
  「同一人物への訂正が 2 セッション以上続き、そのときの距離が閾値を明確に超えている」ケースを
  ログから機械的に検出できるようにする

### 3.5 S5: R3 トークンタイムスタンプ分割【計画済み】

- **狙う誤り**: E2（帰属誤り。特に順次交代の混在セグメントと相槌の巻き込み）
- design 13 §12 の R3 として計画済み。`getTokenTimings()` の API 実在はソース確認済みで、
  未検証は実会議音声での時刻精度のみ（スパイク 3）
- **帰属精度の主要変数**はここにある: chunk 粒度（2240ms）の近似が消えれば、5.2 節の
  「先頭末尾 15% 除外」のようなヒューリスティクスが不要になり、混在表示も激減する。
  E2 に対しては個別チューニング（§3.6）より構造的に効く
- 依存: R2 完了済みなので着手可能。スパイク 3（時刻精度検証）が go/no-go

### 3.6 S6: 帰属・照合パラメタの実測チューニング

- **狙う誤り**: E2・E3 全般（構造は変えず、しきい値を実測に合わせる）
- 対象: 混在表示閾値（30%）/ 中央部計算（先頭末尾 15%）/ `unattributed_grace_ms`（3000ms）/
  `speaker_match_threshold`（0.45）/ `speaker_match_margin`（0.05）/ `min_enroll_speech_ms`（5000ms）
- design 13 §15・design 20 §12 が「実戦で調整」としている項目の実行。**前提は §5 の計測基盤**
  （ラベル付きコーパスと距離ログ集計がないと、調整が場当たりになる）
- `speaker_match_threshold` は既に実測（0.65 → 0.45）で一度動かした実績があり、
  同じ進め方を他パラメタに広げる

### 3.7 S7: Sortformer backend の選択肢追加【計画済みの具体化】

- **狙う誤り**: E1（分離誤りそのもの）
- design 13 §2.1 の実測で、同一音声に対し LS-EEND callhome は 2 話者、Sortformer は 4 話者を
  検出しており、**4 話者以下の会議では Sortformer（DER 20.6% vs 26%）が上位互換になり得る**。
  不採用理由は「話者 5 人以上のハード制限」のみ
- **提案**: `diarization.backend: lseend | sortformer` の config 追加。既定は lseend のまま、
  「リモート参加者が 4 人以下と分かっている会議」でユーザーが opt-in する。
  参加者ヒント（§4.4 F4）が入れば「ヒントの人数が 4 以下なら Sortformer を自動選択」まで
  自動化できる
- **コスト**: 中。FluidAudio 同一パッケージ内なので依存追加なし。coordinator の backend
  プロトコル（`DiarizationBackend.swift`）は既に抽象化されている
- **リスク**: 5 人目が現れたときの取りこぼし。opt-in + ヒント連動に留め、既定は変えない

### 3.8 S8: オフライン再分離（明示的救済）【計画済み・撤退先】

- **狙う誤り**: E1・E2 の総体（リアルタイム分離の品質限界そのもの）
- design 13 §14 のとおり。WAV 全保持のため pyannote + VBx で DER 13.9〜15% の再分離が可能。
  「実行すると slot・手動調整が作り直される」破壊的操作として、Ended セッション限定の
  明示ボタンで提供
- **位置づけを一段具体化する提案**: 全面作り直しではなく、**リアルタイム結果とのアラインメント**
  （オフライン話者クラスタ ↔ 既存 slot を声紋距離で対応付け、既存の実名・訂正を新クラスタに
  引き継ぐ）を挟めば「手動調整が消える」問題は大幅に緩和できる。対応付け不能なクラスタだけ
  Speaker N+1 として増える。これなら「重要な会議だけ、終了後に高精度で作り直す」が
  現実的な運用になる
- **コスト**: 大。優先度は低いが、E1 を根本改善できる唯一の候補なので撤退先として維持

## 4. ユーザーフィードバック面の改善候補

学習を「明示フィードバック起点のみ」に絞った（design 20 追記）ことで、精度向上の律速は
**確認済みサンプルの獲得量**になった。この節の施策はすべて「フィードバックの取得コストを下げる /
機会を増やす / 効くまでの時間を縮める」ことを狙う。

### 4.1 F1: 割り当て提案バッジ（棄却マッチのワンクリック確定）

- **狙う誤り**: E3b・E5
- **現状の制約**: 閾値・マージンで棄却された照合は info ログに残るだけで、ユーザーには
  「Speaker N のまま」としか見えない。惜しい棄却（距離が閾値をわずかに超えた・マージン競合）を
  救う手段が、ゼロからのリネーム操作しかない
- **提案**: 棄却時に最近傍候補を UI に提案として出す。「Speaker 3 — 田中さん？ [はい]」の
  ワンクリック確定バッジ。タイトル自動命名の「提案バッジ」（kikimi.md 8 章）と同じ UX パターンで、
  **自動では反映せず、ユーザーの確定操作を明示フィードバックとして扱う**。
  確定 = `.user` 割り当てなので Ended 時 EMA（α = 0.3）の対象になり、学習にも直結する
- **期待効果**: 「惜しい棄却」の救済が 1 クリック化し、明示フィードバックの獲得量が増える。
  S4（複数声紋）導入後は「そのチャネル用プリントを立てる」入力にもなる
- **提案の出し分け**: 距離が `threshold + 提案余裕幅`（例 +0.10、定数）以内の棄却だけ提案する。
  遠すぎる候補まで出すと誤確定（E3a の人為版）を誘発する
- **コスト**: 中。棄却情報を coordinator → ViewModel に流す経路と、Transcript 行のバッジ UI
- **リスク**: ユーザーが深く考えず [はい] を押す誤確定。α = 0.3 上限 + 声紋リセットの
  既存救済で受容できる範囲。バッジは提案 1 件に限定し、確信度の低い候補は出さない

### 4.2 F2: 訂正のセッション内即時反映（in-session learning）

- **狙う誤り**: E5（訂正が効くまでの遅さ）
- **現状の制約**: リネーム・訂正が声紋 DB に効くのは **Ended 時の EMA が最初**。同じ会議の
  後半で同一人物の新しい slot（世代跨ぎ・分裂）が現れても、訂正前の声紋で照合されるため
  同じ誤り・同じ匿名が再発し、ユーザーは 1 会議で何度も同じ訂正をする
- **提案**: `.user` 割り当て（リネーム・ピッカー・提案バッジ確定）が発生した時点で、
  その slot の embedding を**セッション内限定の照合オーバーレイ**として保持する。
  以降の新 slot の照合は「グローバル DB + オーバーレイ」を候補にし、オーバーレイへの
  マッチは `.auto` 扱いで表示だけ実名化する（**グローバル DB への書き込みは従来どおり
  Ended 時 EMA のみ** — 「学習はユーザー明示起点・Ended 時 1 回」の原則を崩さない）
- **期待効果**: 1 回の訂正がその会議の残り全部に効く。S3（世代跨ぎ再連結）と同じ機構で
  実装できる（S3 は「旧 slot の割り当て」を、F2 は「訂正済み割り当て」を照合元にするだけ）
- **コスト**: 小（S3 実装後）。S3 とまとめて 1 つの「セッション内照合レイヤ」として設計すべき

### 4.3 F3: auto 割り当ての明示確認（confirm）

- **狙う誤り**: E5（学習サンプルの獲得量）
- **現状の制約**: 「訂正されなかった ＝ 正しかった」とみなさない方針（design 20 追記）は
  誤学習を防ぐ正しい判断だが、副作用として **auto 照合が正しかったケースが一切学習されなく
  なった**。声紋が最新の声・チャネルに追従する経路が「ユーザーがわざわざリネームし直す」しか
  ない
- **提案**: auto 割り当ての話者ラベルポップオーバーに「✓ 合っている」を追加する。
  押すと `assigned_by` を `.user` に昇格（表示は変わらない）し、Ended 時 EMA の対象になる。
  非明示の推定は引き続き使わない — **確認もユーザーの明示操作**なので原則と整合する
- **期待効果**: 正例の学習が復活し、EMA が声の経年変化・チャネル変化に追従する。
  操作コストは 1 クリックで、訂正よりはるかに軽い
- **コスト**: 小。ポップオーバーに 1 ボタン + `assignedBy` の昇格書き込み
- **リスク**: ほぼなし（誤確認は誤訂正と同じ α = 0.3 上限で自己回復）

### 4.4 F4: 参加者ヒント（会議前の事前情報を照合の事前分布に使う）

- **狙う誤り**: E3a・E3b の両方（オープンセット照合を名簿によるクローズドセットに切り替える）
- **着想**: 照合が難しい根本原因は「候補が声紋 DB 全体（原理的に無限の未知話者を含む）」である
  こと。**この会議に誰が出るかをユーザーは事前に知っている**のに、その情報を使っていない。
  Draft の準備画面には既に context.md（参加者を書く場所）がある
- **入力 UI（確定方針）**:
  - **任意入力**。指定がなければ従来どおりのオープンセット照合（本施策は丸ごと no-op）
  - **会議前（Draft 準備画面）でも会議中（準備タブ）でも入力・編集できる**。
    導線は準備画面 / 準備タブのみ（会議タブには置かない。context.md エディタと同じ
    ライフサイクルで、実装箇所も 1 つに保つ）。Recording 中の追加・削除は
    **以降の照合に即時反映**し、さらに既存の匿名 slot の再照合（下記）も走らせる
    （refinement の context と違いキャッシュの都合がないため遅延させる理由がない）
  - 入力は**話者 suggest box**: タイプすると既知話者 DB（`voiceprints.json`）を
    インクリメンタル検索して候補を出す。候補にない名前は
    「『田中さん』を新しい話者として登録」の行を選んで**その場で新規登録できる**
  - **未登録話者の新規登録は embedding 空（`embedding: []`）で行う**。これは既存の
    「声紋リセット済み」とまったく同じ意味論に乗る（design 13 §4.4。新しい規約を増やさない）:
    - 距離 `.infinity` 規約により**自動照合には絶対にマッチしない**（声だけ似た別人に
      誤って実名が付くことがない）
    - リネーム・override の既知話者ピッカーには**選択肢として出る**（会議中に本人が
      話したら 1 クリックで割り当てられる。参加者ヒント指定済みの話者はピッカーの
      先頭に優先表示する）
    - 最初のユーザー割り当て後、Ended 時学習が空 embedding へ**新しい embedding を
      丸ごと採用**（実質 α = 1.0）するため、**「会議前に名前だけ登録 → 会議中に 1 回
      割り当て → 次回から自動実名化」**のブートストラップが既存機構だけで完成する
  - 登録はユーザーの明示的な suggest box 操作なので、「声紋 DB への書き込みは
    ユーザー明示起点のみ」の原則（§7）の内側にある
- **話者割り当てからの自動追加（確定方針）**: 会議中にユーザーがセグメント・slot へ話者を
  明示的に設定した瞬間、その話者を参加者ヒントへ自動追加する（未収載の場合のみ）:
  - **トリガはユーザーの明示的な割り当て操作すべて**: slot リネーム（既知話者ピッカー・
    フリーテキスト）・segment override・F1 提案バッジの確定・F3 confirm。
    いずれも「この人がこの会議で発言した」というユーザー自身の表明であり、
    参加者ヒントへの反映はその**派生**にすぎない（auto 照合の結果からは追加しない —
    誤マッチが自分でヒント入りして優先照合が強化される自己汚染ループを防ぐ）
  - **効果**: 参加者リストを事前に手入力しなくても、会議中の訂正が進むほどヒントが
    自動的に充実し、以降の照合が 2 段閾値の恩恵を受ける。「訂正が同じ会議の残りに効く」
    という点で F2（セッション内即時反映）の軽量版を兼ねる
  - **新規名（未登録話者）のタイミング**: 追加は `global_speaker_id` 確定時。名前正規化
    （design 20 §4）で既存話者に解決された場合は即時、純粋な新規名は登録完了
    （WAV フォールバック / Ended 時 enrollment の write-back）の時点で追加する
  - **明示削除の尊重**: ユーザーがヒントから手で削除した話者は、同一セッション内では
    割り当てが再発しても自動再追加しない（suggest box からの手動再追加は可能）
  - mic 側（`self_name`）は対象外（参加者ヒントはシステム音声の照合用）
- **照合への効かせ方（確定方針: クローズドセット切替）**: 2 段閾値のような soft な優遇では
  なく、名簿の有無で照合モードを切り替える:
  - **参加者ゼロ（未設定）** → 従来どおりのオープンセット照合。本施策は丸ごと no-op
  - **1 人でも設定あり** → **照合候補を名簿内の話者に限定する（closed-set）**。
    名簿外の DB 話者には一切割り当てず、名簿内の最近傍が閾値・マージンを満たさなければ
    Speaker N のまま。マージン判定は名簿内の話者同士で従来どおり行う
  - 判断根拠は誤りコストの非対称性: 誤マッチ（E3a）はサマリ・Wiki export に誤った実名が
    残るのに対し、匿名のまま（E3b）は 1 クリックの割り当てで済む。「迷ったら実名を
    付けない」という design 20 以来の方針をヒント設計にも貫く。名簿外の人が実際に
    発言した場合（飛び入り・書き漏れ）は Speaker N として現れ、ユーザーが割り当てた
    瞬間に自動追加（上記）で名簿入りするため、**以降は自動照合の対象に自己修復的に
    復帰する**
  - 参加者数がヒントになる: 指定人数 + 自分を超える slot が出たら分離の過分割を疑える
    （まずはログ・バッジ表示のみ。S7 の backend 自動選択にも使える）
- **名簿変更時の再照合（確定方針）**: 名簿の変更（手動の追加・削除、割り当てからの
  自動追加を含む）のたびに、**匿名のまま棄却されている auto slot を再照合し直す**。
  声紋抽出・照合は slot ごとに一度きり（`extractedSlots`）のため、これがないと名簿は
  「これから現れる slot」にしか効かず、会議中の入力・自動追加の価値が半減する:
  - 対象: `embedding` 抽出済み・`display_name` なし（または `.auto` 割り当てのまま）の slot。
    **`.user` 割り当て済み・accepted 済みの slot は触らない**（既存の保護と同じ）
  - embedding は `speaker_assignments.json` に永続化済みなので、音声の再抽出なしで
    照合だけをやり直せる（安価・S1 と独立に F4 単独で成立する）
  - 削除で名簿外になった話者への既存の auto 割り当ては**巻き戻さない**（表示の突然の
    退行を避ける。誤っていればユーザーが訂正する既存経路で直す）
- **保存（確定方針）**: `sessions/<id>/participants.json` を新設する。内容は
  `global_speaker_id` のリスト + 手動削除の記録（同一セッション内の自動再追加の抑止用）。
  based_on 複製のコピー対象に加える（削除記録はコピーしない）。表示名は
  `voiceprints.json` から解決するためリネーム追従が自動になる。`meta.json`
  （セッション状態機械）とも `speaker_assignments.json`（録音中の auto 書き込みと
  競合管理する場所）とも責務を混ぜない
- **サマリ participants への反映（確定方針）**: 名簿そのものは summary の participants に
  **マージしない**。participants に入るのは従来どおり「実際に発言した（slot・override に
  割り当てが付いた）人」と LLM 抽出のみ。名簿はあくまで照合用ヒントで、欠席者・書き間違いが
  サマリ・Wiki export に載る経路を作らない
- **期待効果**: 定例会議（based_on 複製で参加者ヒントも引き継げる）で照合精度が大きく上がる。
  E3a と E3b を同時に改善できる唯一の施策。未登録話者の事前登録が声紋 DB の
  ブートストラップ経路にもなる（従来は「一度会議でリネームする」しか登録の入口がなかった）
- **コスト**: 中。UI（suggest box + 会議中編集）+ 空 embedding 登録 + 照合候補の
  名簿フィルタ + セッションへの保存。クローズドセット化は照合前の候補絞り込みだけで
  実現でき、`VoiceprintMatchPolicy`（pure function）自体は変更不要
- **リスク**: **名簿の部分入力による退行** — 「初対面の 1 人を登録したいだけ」のつもりで
  名簿に 1 人だけ入れると、書かなかった常連の自動実名化まで止まる（クローズドセットの
  裏面）。緩和策: (a) UI 文言で「入力すると照合をこの参加者に絞ります」と明示する、
  (b) 割り当てからの自動追加により Speaker N を 1 回割り当てれば名簿入りして自己修復する、
  (c) based_on 複製で名簿ごと引き継げるため定例会議では書き直しが発生しない。
  欠席者が名簿に残っている場合は、その人の声紋に閾値内で似た声が来ない限り実害はない
  （オープンセット照合が常に抱えていたリスクの部分集合）

### 4.5 F5: slot 統合操作（「この 2 人は同一人物」）

- **狙う誤り**: E4・E5
- **現状の制約**: 分裂した slot はそれぞれ個別にリネームして表示名を揃えるしかない。
  S3（自動再連結)で大半は消えるはずだが、自動が外したケースの手動回収経路がない
- **提案**: リネームポップオーバーの既知話者ピッカーに「このセッションの他の Speaker」も
  並べる。選ぶと選択先の `display_name` / `global_speaker_id` をコピー（= 既存の
  「同一 global_speaker_id を複数 slot に割り当てる」規約どおり。統合ではなくエイリアス）。
  両 slot の embedding は Ended 時 EMA で同一 speaker のサンプル候補になる（既存の
  slot 分裂時の決定規則に自然に乗る）
- **コスト**: 小。ピッカーのデータソース追加とコピー処理のみ
- **期待効果**: S3 の取りこぼし回収 + 「匿名同士の統合」（DB 未登録の人の分裂）にも効く

### 4.6 F6: 距離ログの可視化（Settings 話者タブの拡張）

- **狙う誤り**: E5（間接的。チューニングと go/no-go 判断の材料供給）
- **現状の制約**: M1 の距離ログは Console.app / `log stream` でしか見えず、
  「なぜこの人が実名にならないのか」をユーザー（= 開発者自身）がその場で診断できない
- **提案**: Settings 話者タブ（design 19）に直近セッションの照合判定履歴を表示する:
  slot / 判定（accepted・rejectedByThreshold・rejectedByMargin）/ 最近傍と距離 / 次点と距離。
  S4（複数声紋）の go/no-go 判断材料（「訂正が 2 セッション続き、距離が閾値を明確に超える」）を
  目視できるようにする
- **コスト**: 小〜中。ログとは別に判定結果をセッションフォルダへ JSON 追記する
  （`voiceprint_decisions.jsonl` など。ログ文字列のパースはしない）

### 4.7 F7: Ended 後訂正の EMA 巻き戻し（pre-EMA スナップショット）

- **狙う誤り**: E3a の残余（Ended 後に誤マッチへ気付いたときの汚染回収）
- design 20 §12 の Open Question。speaker ごとに直前 embedding を 1 世代だけ保持し、
  同一セッション起因の EMA を undo できるようにする
- **判断**: 現状の救済（声紋リセット → 次セッションで手動割り当て → 再学習）で足りている間は
  着手しない。F6 の可視化で「Ended 後に気付く」頻度が観測できてから判断（既存方針を維持）

## 5. 計測基盤（すべての施策の前提）

チューニング（S6）・go/no-go 判断（S4・S5）・施策の効果検証は、いずれも再現可能な計測がないと
場当たりになる。施策より先にここを整える。

### 5.1 ラベル付き評価コーパスと DER 測定ハーネス

- 実会議（Phase 4 の 3 本以上）のセッションフォルダに、正解ラベル
  （セグメント ID → 正しい話者名）を人手で付けた `eval_labels.json` を置く
- 評価スクリプト（mise タスク化）が `diarization.jsonl` + `speaker_assignments.json` +
  正解ラベルから以下を算出する:
  - セグメント帰属の正解率（E1+E2 の複合指標。表示規則を通した最終表示 vs 正解）
  - 照合の precision / recall（E3a / E3b を分けて見る）
  - slot 分裂数（E4。正解話者あたりの slot 数）
- WAV・JSONL が全保持されているので、**過去セッションに対して施策の before/after を
  オフライン再実行で比較できる**（照合ポリシー・帰属ロジックは pure function 化済みで、
  録音なしに入れ替え評価が可能）。これが本基盤の最大の価値
- 加えて kikimi-verify 用の決定的な複数話者ダミー音源（design 13 スパイク 6）を整備し、
  回帰テストとして CI 相当（`mise run verify-smoke`）に組み込む

### 5.2 距離ログの機械集計

- F6 の `voiceprint_decisions.jsonl`（照合判定の構造化記録）をセッション横断で集計する
  スクリプトを用意し、同一人物・別人の距離分布、棄却理由の内訳、訂正が繰り返された speaker を
  一覧できるようにする
- S4（複数声紋）・S6（閾値調整）の判断材料はここから出す

## 6. 優先順位と推奨順序

評価軸: 効果（狙う誤りの発生頻度 × 改善幅）/ コスト / 依存関係。

| 順 | 施策 | 狙い | コスト | 依存 | 備考 |
|---|---|---|---|---|---|
| 1 | 計測基盤（§5） | 全部の前提 | 中 | なし | Phase 4 実戦と並走で正解ラベルを作る |
| 2 | F3 confirm ✓ | E5 | 小 | なし | 最小コストで学習サンプルが増える |
| 3 | F1 提案バッジ | E3b・E5 | 中 | なし | 棄却ログは実装済み。UX パターンも既存流用 |
| 4 | S3 + F2 セッション内照合レイヤ | E4・E5 | 中 | なし | 2 施策を 1 設計で。体感改善が最大級 |
| 5 | S1 漸進的再照合 | E3b | 小 | なし | S2（品質ゲート）を同時に入れると効果が乗る |
| 6 | S2 品質ゲート | E3a/b | 小〜中 | S1 と同時推奨 | |
| 7 | F4 参加者ヒント | E3a・E3b | 中 | なし（未登録話者の事前登録が DB のブートストラップになる） | 定例会議で効果大。任意・会議中編集可・suggest box（§4.4） |
| 8 | F5 slot 統合操作 | E4 | 小 | S3 の後（取りこぼし回収） | |
| 9 | F6 距離ログ可視化 | 診断 | 小〜中 | `voiceprint_decisions.jsonl` | 1 の計測基盤と共通化 |
| 10 | S4 複数声紋 | E3b | 中 | 計測基盤の実測で go/no-go | 設計は 13 §14 で確定済み |
| 11 | S5 R3 トークン分割 | E2 | 大 | スパイク 3 が go/no-go | 帰属精度の本丸 |
| 12 | S6 パラメタ調整 | E2・E3 | 小（反復） | 計測基盤 | 常時継続の営み |
| 13 | S7 Sortformer opt-in | E1 | 中 | F4 があると自動化可 | |
| 14 | S8 オフライン再分離 | E1・E2 | 大 | 上記で不足と判明したら | 撤退先として維持 |

推奨する進め方:

1. **まず計測**（§5）。Phase 4 の実戦 3 本にラベルを付け、E1〜E5 それぞれの実測頻度を出す。
   どの誤りが体感を最も損ねているかで 2 以降の順序を入れ替えてよい
2. **次にフィードバックの獲得量を増やす**（F3 → F1）。学習を明示起点に絞った現方針の
   ボトルネック解消が先で、ここが増えないと S4 以降の学習系施策の材料も揃わない
3. **セッション内で完結する自動改善**（S3+F2 → S1+S2）。DB の成長に依存せず、
   初対面ばかりの会議でも効く
4. **事前情報と大物**（F4 → S4 → S5）は実測データが揃ってから

## 7. 不変条件（全施策共通で守ること）

既存設計の原則をすべて維持する。本資料のどの施策も以下を破らない:

- **録音は絶対に止めない**（kikimi.md 6 章）。diarization は全経路 best-effort
- **transcript.jsonl / diarization.jsonl は追記のみ・不変**。話者情報は sidecar と表示レイヤで解決
- **声紋 DB への書き込みはユーザーの明示的フィードバック起点のみ**（design 20 追記の方針）。
  F1 の提案確定・F3 の confirm・F5 の統合・F4 の suggest box での新規参加者登録
  （空 embedding）はいずれも明示操作であり、この原則の内側にある。
  F2 のセッション内オーバーレイは表示専用で DB に書かない
- **user 割り当ては auto で上書きしない**。S1 の再照合・S3/F2 のセッション内照合も同様
- **slot は不変・統合しない**。同一人物の多重 slot は同一 display_name / global_speaker_id の
  割り当てで表示上吸収する（S3・F5 はこの規約の上に載る）

## 8. Open Questions

- セッション内照合レイヤ（S3/F2）の閾値をグローバル照合より緩くできるか
  （同一会議・同一チャネルなら距離分布が締まる仮説。計測基盤で検証）
- F1 の提案余裕幅（threshold + いくつまで提案するか）の初期値
- F4 のクローズドセット照合時、名簿内の閾値を通常（0.45）より緩められるか
  （候補が数人に絞られる分、偶然の閾値内他人が減る。計測基盤の距離分布で判断）
- S1 の再抽出トリガ段数（5/15/30s 案）と「accepted 後は格下げしない」以外の確定条件
- 評価コーパスの正解ラベル付け UI を作るか（当面は JSON 手書きで足りる想定）
